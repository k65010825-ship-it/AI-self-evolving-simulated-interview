# 映射到观澜

本文件是对当前产品的建议，不是Craft源码事实。开始修改前重读本地实现与当前任务；完成度以实际测试与现场记录为准。

## 已有所有者与可借鉴的边界

| Craft参考 | 观澜现有入口 | 借鉴方式与不变量 |
| --- | --- | --- |
| core类型、protocol、统一事件 | src/runtime/contracts.ts、research-backend.ts、research.ts | 契约与执行实现分开；需要的是稳定事件语义，暂不为外观拆包 |
| server-core/SessionManager | workbench-store.ts、workbench-api.ts、workbench-server.ts | 应用服务管理提交、存储、运行归属与UI交付；避免把工具或SDK逻辑堆进HTTP handler |

| 执行侧权限与前置检查 | ResearchHarness、beforeTool、工具Schema与提交领域校验 | 区分参数校验、权限、预算、业务证据校验；每外部输入只校验一次，执行策略按当前状态生效 |
| 配置来源、凭证与激活 | read/search依赖、未来ConnectorConfig | 与ResearchSource证据原文分离；不把搜索摘要当证据，不先扩外部权限 |

| 自动化回到会话服务 | 未来定时/事件调查入口 | 调用同一任务应用服务和预算，不在定时器中复制Agent Loop |

## 一个可验证的下一步：取消调查

问题：浏览器关页不停止后台任务，当前底层支持AbortSignal不等于用户已有取消入口。

建议所有权：应用层为每个活动run管理取消句柄；HTTP取消命令映射到该run；Harness确定取消终态并向模型/在途工具传播；存储保存取消结果；UI显示已取消及已有证据。后端适配翻译取消机制，不把SDK对象塞进UI或持久化文件。

验收至少包括：取消等待中的模型、取消读正文、已经完成后再取消、取消与完成同时到达；验证原调用确实结束、终态不反转、失败尝试计数保留，不产生自动补跑。这是设计与验收建议，需结合现有代码实现，不能声称已经完成。

## 接下来的取舍

1. **Harness事件与恢复：** 先定义事件序号、run归属、预算预占与实际工具回执；明确哪些状态可以恢复、哪些要标记未知/中断。不要把保存UI进度称作完整checkpoint。
2. **记忆：** 先保存可追溯事实与任务摘要，标明来源/时间/有效性/版本，支持冲突、修正与删除；在证据模型确定后再选关键词、结构化或向量检索。
3. **工具调用：** 工具契约、执行准入、来源身份、错误与超时、重复调用、重试额度分别验证。没有外部写操作时不先引入复杂审批平台。
4. **自动化与RSI：** 自动触发不扩大权限，策略候选不自行晋升。保持真实调用有预算、保留独立评测与失败记录，再考虑定时、后台和策略回滚。

不应仅为“参考Craft”而采用Bun/Electron、复制SessionManager大类、增加Claude双后端、把全部工具改成MCP、堆向量库，或引入会突破当前硬预算的自动重试。
